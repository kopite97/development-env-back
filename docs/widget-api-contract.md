# Widget and Dashboard contract

Approved scope: PLAN-0013. Session 1 contract freeze; implementation and production readiness are separate checks.

## Configuration and layout

Widget create: `{type,title,configVersion:1,config}`. PUT: `{revision,title,configVersion:1,config}`; type is immutable. Title trims Java whitespace and is 1-48 UTF-16 units. The six existing types use `{selection,limit?}`. Selection is exactly `{kind:"all"}`, `{kind:"uncategorized"}`, `{kind:"project",projectId:UUID}`, or `{kind:"category",categoryId:UUID}`. Limit is an optional integer 1-20, forbidden for links/deploy; deploy requires all. Absence is preserved, never persisted as a default or null. Reject unknown, duplicate, null, coerced and response-only fields. UUID input accepts canonical hyphenated syntax, case-insensitively; output is lowercase.

Widget responses contain id/type/title/configVersion/revision/config/referenceState/createdAt/updatedAt. Reference state is computed `valid | missingCategory`, not stored or writable. Missing Category retention applies only to the unchanged selection of the same saved Widget. New missing/foreign references return 404; any broken Project reference returns 404. Saved unresolved Category data returns 200 unavailable/unknown, null data/page, REFERENCE_MISSING, retryable=false. Do not disclose cross-workspace existence or infer deletion provenance.

Widget list: `limit` 1-100 (default 20), optional `unplaced=true|false` (omitted and false both mean all), optional cursor. Return `{items,nextCursor}` ordered createdAt DESC, id DESC. Cursor is opaque, HMAC-SHA256 authenticated with the existing signing key, and binds workspace/limit/unplaced/order. Malformed, tampered or mismatched cursors return 400 INVALID_CURSOR. No new workspace-wide snapshot pagination guarantee is introduced.

Layout PUT: `{schemaVersion:3,layoutRevision,placements:[{widgetId,size}]}`. Size is small/medium/wide, validated against the type definition. Placement IDs are response-only server UUIDs. Match existing placements by widgetId to preserve identity across order/size changes; removing and reattaching gets a new ID. Duplicate widgetId is invalid. No new count cap. Response is `{id:"home",schemaVersion:3,initialized,layoutRevision,placements:[{id,widgetId,size}],widgets:[WidgetResponse]}`; array order is placement order. Load configurations/references in batches in one RR transaction.

Unsaved GET: false/0/empty arrays without writes. First PUT at 0 creates revision 1 even when empty; it creates no Widgets. Initialization POST `{schemaVersion:3,layoutRevision:0}` creates exactly the existing six defaults and six placements, each Widget revision 1, layout revision 1. Existing layout causes 409 REVISION_CONFLICT unless an unexpired matching replay is found first. Migrated saved-empty stays initialized at its original positive revision. Every fresh command increments workspace dataRevision once; unchanged PUT increments its resource revision. Widget delete requires single positive `revision` query and no body; referenced deletion is 409 WIDGET_IN_USE, repeated deletion 404. Safe-integer bounds and existing workspace overflow rules apply.

## Typed local data

All payloads have `kind` equal to the Widget type. Only board/journal/milestone accept an optional cursor on `/data`; all other query parameters, including filter/limit overrides, are rejected. Their page is `{total,nextCursor}` with a Widget-bound cursor; others have page=null. Bind workspace, Widget ID, configuration revision, type, effective limit and business cursor. A configuration change invalidates old cursors with 400 INVALID_CURSOR. Do not change existing business cursor codecs. Key material and authentication secrets are never returned.

| Type | Payload fields after kind | Read semantics / empty predicate |
| --- | --- | --- |
| overview | projects: ProjectCategoryCount[], tasks: {todo,doing,done,total,asOf} | Existing Overview filter/aggregation; limit preserved but not applied to aggregate. Empty iff all project counts and task total are zero; retain zero buckets. |
| board | columns: [{status,items:TaskSnapshot[]}], statistics: {todo,doing,done,total,asOf} | One global task page, deleted=false, status absent, projectStatus=all, query empty; group in todo/doing/done order retaining page order. Default limit 20. Statistics count all matching tasks independently of limit/cursor. Empty iff returned page has no items. |
| journal | items: JournalSnapshot[] | projectStatus=all, query empty, from/to absent, newest; default limit 3. Empty iff returned page is empty. |
| milestone | items: MilestoneSnapshot[] | projectStatus=all, status=open; existing due-date/ID order, default limit 2. Empty iff returned page is empty. |
| links | items: LinkSnapshot[], collectionRevision | Existing Link query with projectStatus=all/query empty, ordered position/id; no limit/page. all includes unlinked; uncategorized includes unlinked and uncategorized-Project links. Empty iff items is empty. |
| deploy | no payload | Always unavailable/unknown, NOT_CONFIGURED, retryable=false; no external call. |

Snapshot item fields are the immutable application read-model fields in task/journal/milestone/link `application/model/*Snapshot.java`, excluding their JsonIgnore dataRevision; no ORM entity is returned. ProjectCategoryCount is `{categoryId:null|UUID,active,archived}`. Stats fields are nonnegative counts and ISO-8601 asOf. Lists retain typed empty arrays. These are fixed DTOs, not arbitrary payload maps.

Envelope: `{widgetId,type,configRevision,configVersion:1,payloadVersion:1,availability,freshness,readAt,sourceObservedAt,lastSuccessfulSyncAt,data,page,problem}`. Local reads observe configuration, authorization, data and X-Workspace-Data-Revision in the same RR transaction. All timestamps are ISO-8601 instants or documented null; local sourceObservedAt/lastSuccessfulSyncAt are null. `readAt` is application read time, not DB commit time. Matrix in PLAN-0013 is normative: current ready/empty has typed data and null problem; stale ready/empty requires typed data and permits a safe problem; unavailable requires unknown/null data/null page/non-null problem. Stale support is envelope validation only, not a cache/integration implementation. Unexpected failures remain 5xx.

Frontend evidence (read-only): sibling frontdev ServerDashboardHome uses defaults 20/3/2; TaskReads.TaskBudget pages globally with independent stats; ApiLinks uses existing category/project filtering. Homepage filter overrides, search UI and renderer composition remain frontend concerns; this API reads saved configuration only. Overview is an aggregate payload rather than the existing frontend's combined Project list/overview component. Frontend adaptation is required and not implemented here.

## Replay

Use a dedicated workspace-owned table for Widget create and layout initialization. Primary key `(workspace_id,method,path,key)`, method POST, paths `/api/v1/widgets` and `/api/v3/dashboards/home/initializations`. Store hash, status=201, exact serialized body text, original Location, created_at and expires_at. No Widget FK. Key is 1-128 visible ASCII characters. Expiry is initial command Clock instant truncated to microseconds plus 24 hours; expired iff expires_at <= now, no extension. Authenticate/validate static input, then workspace-lock and check hash/replay before live references or initialization conflict. Replay returns original body/Location even after deletion, omits workspace revision header, preserves no-store and makes no mutations. Expired rows may be removed only within fresh operations. Current-state GET after replay is required; 404 is valid.

Fingerprint: SHA-256 of big-endian int32 version=1, then length-prefixed UTF-8 canonical path and canonical request JSON. Canonical JSON recursively sorts object keys lexicographically, has no insignificant whitespace, retains array order and raw string values, and preserves absent fields. Numbers in accepted requests are integers; serialize their integer decimal value. Reject duplicates/null/unknowns before hashing; do not trim title strings or normalize UUID string case for this hash. Thus object key order/JSON whitespace do not affect it; raw value or omission changes do. Initialization canonical JSON is `{"layoutRevision":0,"schemaVersion":3}`, expected digest `b311d35dafc88f0b20e0ae705f819a8c67f42892f46e4f9de8a832c9eb3d85c5`. Type configurations use this same traversal; no per-type hash algorithm is needed.

## Migration identity and prerequisites

Use UUID v3 (standard name-based MD5 with version/variant bits), available in Java/PostgreSQL without a dependency or extension. Name UTF-8 bytes:

`devspace-widget-backfill-v1|{kind}|{lowercaseWorkspaceUUID}|{UTF8-byte-length(dashboardKey)}:{dashboardKey}|{UTF8-byte-length(legacyId)}:{legacyId}`

Kind is `widget` or `placement`, defining separate fixed namespaces. Exact already-valid legacy IDs are retained, without trimming during migration. For workspace `00000000-0000-0000-0000-000000000001`, dashboard `home`, legacy ID `home-board`: Widget `e80ce8b8-a78c-3dc4-9337-e62c359c39b9`, Placement `ce732f96-b7f5-3a8a-8334-cfdbb1a7ad62`. MD5 here supplies deterministic identity, not authorization or security. Unique constraints and reconciliation detect collisions; stop rather than regenerate. Mapping rows are immutable audit history and deliberately have no live Widget/Placement FK, so valid later deletion does not erase or block history.

V18 implements the Widget migration. Package it after V17, require successful V17 history and no remaining scope columns, and retain V17 checksums/drain. Preserve legacy JSONB/revision/timestamps; add separate layoutRevision/timestamps. Saved arrays, including empty, migrate atomically; absent dashboards stay absent. Validate schema/type/shape/title/selection/limit/owned Project and revision capacity before writes; unresolved saved Category IDs are retained. Reject unsupported/invalid data, duplicate IDs, mismatched mapping, UUID collision and overflow. Store exact mapping by workspace/dashboard/legacy ID; do not silently overwrite. Increment workspace counter once per saved dashboard workspace, including saved-empty, in the same transaction. Stop/drain old writers before migration; v1 already retired, retire v2 Dashboard on switch. Preserve old data/mapping; cleanup is excluded.

Final-only artifact policy is approved; prior bridge baseline evidence and current final build/migration tests are recorded under docs/reviews/plan0013. No production state has been verified. Backend validation and frontend/production readiness remain separate.

## Frontend handoff sequences

1. Fetch the authenticated type catalog and Home layout. Unsaved is an explicit state: offer initialization POST for defaults or PUT with empty placements. Never initialize as an effect of GET or overwrite a saved-empty layout.
2. Layout includes all referenced configurations; do not issue one configuration GET per placement. Fetch `/widgets/{id}/data` for visible placements. Catalog schema supplies configuration validation; each payload kind needs a supported frontend renderer. No integration credentials or cache management API is provided.
3. Create an unplaced Widget with a new Idempotency-Key. Preserve that key/body for retries. Use the returned ID in a layout PUT with the current layoutRevision; the request contains widgetId/size, never placement id. If layout PUT conflicts, preserve the draft and the unplaced Widget; list with unplaced=true to recover it. Do not automatically delete it.
4. Replace a Widget with its own revision. A fresh successful response is the authoritative saved configuration, so an immediate configuration GET can be omitted. It does not include display data or refresh other affected resources: fetch data for the new configRevision. Layout saves similarly return the saved layout/configuration snapshot. GET after a lost response reconciles current state; never blindly retry a stale PUT.
5. A historical POST replay has no X-Workspace-Data-Revision. Its body and Location are original operation results, not evidence that the resource still exists. GET current state before adopting it; a deleted Widget may return 404. A changed payload needs a new key, not reuse of the old operation key. No ETag/If-Match protocol is added.
6. Remove a placement through layout PUT, then optionally DELETE the unplaced Widget with `?revision=...`. These are separate operations and can partially succeed. DELETE returns `{id}`; a remaining reference returns WIDGET_IN_USE. No automatic orphan cleanup.
7. Compare workspace header values as decimal strings/BigInt, never JavaScript Number. Resource edit revisions are safe integers. Reject data from an older configRevision and restart paging after edits; discard delayed older workspace observations according to the existing session cache policy. A matching configRevision does not promise the latest DB commit after a read began. Backend snapshot consistency and frontend response ordering are separate responsibilities.
8. Render retained missingCategory as an editable configuration warning; data is unavailable/REFERENCE_MISSING, not an empty board. Broken Project or foreign Widget is 404. Deploy remains unavailable/NOT_CONFIGURED. Typed empty payloads retain arrays and zero buckets. Handle null source times without inventing sync timestamps. Unexpected 5xx, 401/session clearing, disabled-account and CSRF handling stay unchanged.

Pagination uses one forward cursor per list. Board's limit is global across columns, statistics cover the whole matching collection. New matching writes may change totals/order between requests; there is no long-lived DB snapshot across pages. Invalid cursors return the existing ApiError format with INVALID_CURSOR; refetch page one. Frontend memory TTL/refresh policy is independent of this backend, which adds no Redis or scheduler.

Complete schemas are published at public `/v3/api-docs` and Swagger UI; Widget/layout operations require the existing authenticated session. [Complete HTTP examples](reviews/plan0013/http-examples.json) contain the six create/data responses and layout states captured from isolated API tests. Nullable object fields use explicit object-or-null unions in OpenAPI 3.1; payload kind has explicit discriminator mappings. API versions are resource-specific: new Widgets v1, breaking Home layout v3, retired Dashboard v2=410. Frontend changes and production deployment have not been performed. Follow the separate [cutover and recovery procedure](widget-rollout.md) before any approved production switch.
